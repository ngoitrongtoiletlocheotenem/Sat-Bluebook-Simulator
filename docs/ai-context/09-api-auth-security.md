# API, authentication, and security

[Context index](README.md)

Source-verified on 2026-10-19 against [`server/app.ts`](../../server/app.ts), [`server/auth.ts`](../../server/auth.ts), validation, and domain handlers. This is a complete inventory of declared API handlers at this snapshot, including aliases. It documents implementation and limitations; it is not a security audit or a claim that tests ran during this documentation task.

## Transport and inventory conventions

The browser calls same-origin `/api` using cookie sessions. Unless indicated otherwise, responses are JSON and mutations use JSON bodies. Multipart routes accept a `file` field. No bearer-token/API-key auth, OAuth, public signup role selection, WebSocket, or external AI provider endpoint is implemented.

Roles in tables: **Public** = no valid session required; **Signed in** = student/teacher/admin; **Author** = teacher/admin; **Admin** = admin only. Ownership restrictions are additional to role checks. Every session-authenticated mutation needs `x-csrf-token`; Origin rules also apply to anonymous mutations. Status is normally 200; creation endpoints explicitly return 201. Validation errors are summarized later.

Response shorthand references [`shared/types.ts`](../../shared/types.ts): `Question`, `Blueprint`, `Attempt`, `Result`, `ReviewItem`, `Domain`, `QuestionAsset`, `HistoryItem`, and `Dashboard`. Server Zod schemas are authoritative where types differ.

Question visibility is always shared (`owner_id IS NULL`) plus current user's private records. Admin does not bypass another private owner's scope. Students see only published shared records plus their own records; authors see shared draft/archive records too. Non-admins never receive `adminNotes` through bank serializers. Answers, explanations, and choice rationales **are** available in the learning library to students; only active attempt content is redacted.

License presence is syntactic validation, not permission verification.

Rich fields cap input at 100,000 characters and sanitize allowed formatting, tables, and images using sanitize-html. Other notable limits: publicId 120; correct/accepted answer text 100; up to 20 accepted answers, 30 tags of 60 chars, ten images, ten structured assets; source 500; license 3000; adminNotes 10,000. Full schema and defaults: [`questionSchema`](../../server/validation.ts).

Attempt input: required `mode` full/module/practice/tutor/wrong/weak/bookmarks; optional blueprintId, section, domainId, skillId, difficulty, count integer 1–100, seed ≤100, excludeSeen/includeWrong booleans, timeMultiplier 1/1.5/2, breakSeconds 0–3600, questionIds ≤100, timedSeconds 30–14400, tags ≤30, source ≤500, domainDistribution record with each weight 0–100. Weighted distributions require a selected section and random practice assembly, and disallow full/module mode, blueprintId, or manual IDs. At least one positive weight is needed; selected domains must belong to that section.

Saved responses are a record keyed by question ID. Each supplied value must contain `answer` ≤100, `eliminated` choice IDs max five, `marked` boolean, `highlights` max 100, `note` ≤10,000, `elapsedMs` 0–86,400,000. Full deadlines continue while disconnected; GET can close and grade expired modules. Future questions never appear in the attempt payload. Completion makes saved report/review available. Immediate grading is limited to tutor mode. Full attempts cannot pause; custom modes can.

| `POST /api/assets`                        | Signed in + CSRF                                                 | Multipart file; PNG/JPEG/WebP magic bytes, max 5 MB                                                                             | 201 `{id,name,url,size,mimeType,createdAt}`                             | app inline / question_assets + filesystem |

The multipart helper uses in-memory storage, at most one file and ten text fields, and `defParamCharset:'utf8'` so Unicode original filenames display correctly. The application does not trust uploaded extension/MIME. PNG eight-byte signature, JPEG first three bytes, or RIFF/WEBP header determines generated extension/type. It does not decode the whole image, verify dimensions, transcode, OCR, extract a graph, or scan for malware. SVG/GIF are not accepted by this upload API. Public seed SVGs are a separate static asset source.

Parser limits: only .csv/.xlsx/.json recognized; CSV max record size 100,000 and strict column counts; JSON must resolve to an array or `{questions:[]}`; XLSX uses first worksheet, first row's exact text headers, cell `.text`, nonempty data rows, and ignores drawing/image anchors. Max 5000 rows. XLSX scans ZIP central-directory sizes and rejects declared expanded total >30,000,000 bytes before ExcelJS. This is a bounded input check, not a formal ZIP-bomb proof. Malformed XLSX gets 422 `Invalid XLSX workbook`; no parsed rows means no per-row repair UI.

Per-row images: canonical `images` array supports HTTPS or local `/assets/...` and `/uploads/...`; CSV/XLSX accept JSON array text or comma/semicolon-delimited strings. Data URLs, `C:\...`, `file://`, relative desktop paths, and embedded workbook drawings do not produce importer image URLs. Importer checks local paths remain under the configured root, resolves symlinks with realpath, and requires an existing file. HTTPS is syntax/hostname checked only; no network availability or content request occurs. Local files are checked again on confirmation.

Repair workflow is **manual per question**: parse first → locate missing/invalid image errors or add a needed figure → upload through `/api/assets` → save resulting URL array to that preview row → revalidate → confirm. Empty image arrays are valid for text-only questions. Repair accepts valid URL syntax even when a local file remains absent, but keeps that row invalid with image errors; invalid URL schema syntax receives 422. It does not repair academic text, answer keys, taxonomy, licenses, or the workbook package. It may remove a bad reference by replacing the image array. The endpoint can change only `images`, not structured `assets` or HTML `<img>` content.

Preview duplicate checks compare visible public IDs and SHA-256(section + normalized stem + normalized passage), including within-upload duplicates. This excludes choice/answer/image changes. Duplicate decisions stay frozen during image repair. Database publicId uniqueness is global and can still reject a private ID collision that preview could not see. Confirm skips invalid/duplicate rows and persists a report transactionally; it is not all-or-nothing validation of the entire uploaded question set.

## Passwords, cookies, sessions, CSRF

[`auth.ts`](../../server/auth.ts) normalizes email to lower-case/trim. Registration first validates email format and max 320; login accepts a string max 320. Registration requires a trimmed 1–100 name and password minimum ten characters, maximum 128 characters and 72 UTF-8 bytes (bcrypt's limit). Login shares maximums without enforcing the registration minimum. Unknown email and wrong password return the same 401 message. Hash cost is 12. No password-reset/change, MFA, email verification, lockout persistence, or login audit log is implemented.

`makeSession` generates 32 random bytes each for session token and CSRF token. SQL stores SHA-256(token), never the raw cookie. Cookie `sat_session` is HttpOnly, SameSite=Lax, path `/`, expires seven days, and Secure only when `NODE_ENV=production`. Expiry is absolute, not refreshed on use. Authentication joins current users and ignores expired sessions, so role changes are also read from current account data. Logout deletes only the current session; admin role changes invalidate every target-user session. Expired rows have no automatic collector.

CSRF middleware runs after optional authentication on `/api`, except health. GET/HEAD/OPTIONS skip checks. Other methods:

1. If Origin exists, it must equal `APP_ORIGIN` or `${req.protocol}://${req.get('host')}` exactly.
2. If authenticated, `x-csrf-token` must equal the session's CSRF token, including logout.
3. If Origin is absent and `Sec-Fetch-Site: cross-site`, reject.

Anonymous register/login still receive Origin checks but do not require a session token. A non-browser client with no Origin/Fetch-Site is allowed by those checks; it still needs a session and CSRF token for protected mutations. No permissive CORS middleware is installed. Set Origin/trust-proxy/HTTPS consistently at deployment; malformed reverse-proxy configuration can undermine assumptions about protocol/host and rate limiting.

Global API rate limit is 600 requests per 60 seconds; login/register also share a limiter of 40 per 15 minutes. Both use draft-8 standard headers and no legacy headers. Stores are process-local defaults, not a distributed limiter. No separate upload-byte quota, per-account asset quota, or total stored-import cap exists.

## Content, media, and path safety

The server sanitizer allowlists basic rich text/table tags, limited attributes, and HTTPS image schemes; client rich rendering additionally uses DOMPurify. Sanitization is not licensing verification or academic validation. `safeUrl` syntax allows HTTPS or a local `/assets/`/`/uploads/` character set; it does not fetch a URL. Direct question create/update applies URL syntax only; importer adds root containment/existence checks **only for the images array**. `safeUrl` itself permits dot segments, so do not treat regex validation alone as full path safety.

Asset storage derives paths solely from generated UUID plus detected extension. `basename` after backslash normalization removes path components from display filenames; control characters are stripped, names trimmed and capped 255 characters, with fallback image name. Original UTF-8 display labels are never used to select disk paths. Exclusive `writeFileSync(...,{flag:'wx'})` avoids replacing an existing file. Failed DB insert attempts unlink of the new file. A filesystem/SQL crash window still exists; no asset deletion/orphan reclamation route is implemented.

**Uploaded images are public URLs.** Owner metadata in `question_assets` limits the image-picker listing, not file delivery or attachment URL reuse. Question content contains URLs, not owner-checked asset IDs. A user who has a URL can read or reuse it. Avoid promising confidential media or tenant isolation based on the current table's owner column. Backups must include upload files as well as SQL.

## CSP and Desmos isolation

Configured main-page CSP in app: default/self, scripts self + `https://www.desmos.com`, styles self + unsafe-inline, images self/data/https, fonts self/data, connect self + Desmos, frame self + Desmos, worker self, object none. Insecure-request upgrade is enabled only in production. Helmet supplies its other default protections. **Main script policy does not allow unsafe-eval.**

[`client/Calculator.tsx`](../../client/Calculator.tsx) embeds calculator HTML with `sandbox="allow-scripts"` and no allow-same-origin, yielding an opaque origin. Only the calculator HTML response allows unsafe-eval for Desmos v1.12 generated code, uses restrictive default-none CSP, frame-ancestors self, base-uri none, form-action none, object none. Its bridge JS needs CORP cross-origin because an opaque sandbox cannot load same-origin-only resources.

Parent and frame use postMessage with `'*'` because the sandbox origin is opaque. Their check is **event.source identity**, not event.origin: parent accepts messages only from its frame contentWindow and allowlisted types; bridge accepts init only from window.parent, only once, with bounded nonblank key and constrained version. Configured key is browser-visible by design; never copy an actual local key into docs. Bridge dynamically loads official Desmos, times out failures, and destroys/disconnects on teardown. Do not weaken main CSP or add allow-same-origin to fix calculator issues without reviewing this isolation design. Source: [`client/desmos.ts`](../../client/desmos.ts), [`public/desmos-calculator.js`](../../public/desmos-calculator.js).

## Error contract, operational risks, and verification pointers

JSON errors use `{error:string}`: Zod issues 422; ApiError's explicit 400/401/403/404/409/413/415/422 etc.; Multer size 413 and other Multer rejection 400; malformed request body 400; unexpected failure generic 500 with error name logged only. Database health does not reveal configuration. The generic Multer message always mentions the 5 MB maximum even for other rejected multipart conditions. JSON parser's `2mb` limit is configured, but non-ApiError status 413 is not explicitly mapped by the current catch-all and can become generic 500.

There is no role/tenant check for teacher/admin student statistics beyond the role gate. Bank answers are intentionally available for self-study, so attempt redaction does not create anti-cheating isolation from the bank. Public uploads remain readable after metadata changes and can outlive accounts. Auth/account/upload lifecycle features listed as absent above should not be inferred from UI labels or old docs.
